M4.5
Colour pipeline Complete · 111 tests

The approved grade from the colour session, applied to everything the tool writes. Core only, no interface.

color.py/clf.py/render.py/exr.py
Respecified on 11 September, when the studio described how colour actually works here. Colour is finished before the tool runs: the AD meeting decides the look, a grading session builds it, and that session exports an updated final edit list plus one colour transform per shot. The tool applies those and never authors any colour, which is why the four on-screen colour controls and the three frame viewers that were planned that morning have both been removed. What changes: shooters deliver one log format no matter what camera they shot on, which removes an entire class of per-camera problems before it starts. Every delivered file carries the approved look, plates included, and every plate records exactly which version of the grade is in its pixels, so a frame can be traced back months later without the grading session. A shot whose colour has not arrived is not delivered ungraded; it is not delivered. The first part is built. The colour engine is in, pinned to the same industry standard version the grading session runs, and it carries the two ends of the chain: reading the shooters' format, and producing the wide scene-referred form the plates are delivered in. It ships no configuration files of its own, so there is nothing for an installer to place or a user to point at. The question about which log format the shooters deliver in no longer holds anything up: the format is one name in one setting, checked when a run starts, so whichever answer comes back costs a single word and no rebuilding. Matching the grade to the shot is built, and it refuses to guess. The session's edit list is now what the tool conforms from - it carries the approved in and out points as well as the colour - and each shot is paired with its own colour file by the shot code in the name. A shot the tool cannot match gets no grade and is reported, rather than being given the nearest one: a neighbouring shot's colour looks entirely plausible and would ship. Two shots claiming the same colour file stops the run rather than picking one, for the same reason. Every colour file is also opened and measured before it is trusted, because the one failure that cannot be seen on a monitor is a colour file that already contains the viewing transform: the plate would then be a picture of the look rather than the wide scene-referred original, and it would look completely normal until someone tried to work on it. A fingerprint of each colour file is recorded with every frame it touched, so a plate can be traced to the exact version of the grade months later. The viewing copies' colour is built too. The whole viewing chain - the shooters' format, the approved grade, and the industry standard viewing transform - is collapsed into a single lookup table per shot, which is how the video tool applies it in one pass without frames passing through the application at all. It is checked from both ends: the colour engine reads the table back as the chain it was built from, and the video tool itself is run against it and lands within a quarter of one code value of the engine's own answer. Which viewing transform, the last part of a question first asked a fortnight ago, now has a built default: the standard one, since the other three the library offers are a simulation of a different display, a debug view and no transform at all. The last part is built, and the chain now reaches the files. Plates are written with the approved look in them, in the wide scene-referred form, and each frame states what was done to it: which colour file, its fingerprint, which format the source was read as, and the readable short form of the grade for anyone without colour software - with a line in the file saying which of the two was actually applied, since carrying both is only safe if the file says. Reference videos are encoded through the lookup table, in one pass, which corrects what they have looked like since they were first built and closes the oldest item on the list. One picture is deliberately left ungraded. The reference stills - the colour chart, the grey and mirror balls, the size reference - are what a compositor matches lighting and colour against, and a creative grade applied to a colour chart destroys the only thing the chart is delivered for, while still looking exactly like a chart. They are converted to the delivered form like everything else and the look is never put on them. What is left is not code. Pointing the tool at a grading session is a flag on the command line today and becomes a setting in the interface, and the checks that refuse to render a shot whose colour has not arrived switch on with it. Both are M5.

Corrections made to the spec

The colour chart must never be given the grade

The rule for this pipeline is that everything the tool writes carries the approved look. Building the last part of it turned up one thing that must not: the reference stills. A shot can arrive with a colour chart, a grey ball, a mirror ball or a size reference shot beside it, and every one of those exists so a compositor can match lighting and colour against a known quantity.

Putting a creative grade on a colour chart destroys the only thing it is delivered for, and it does it invisibly: the chart still looks like a chart, and the artist matching against it has no way to tell. Nothing in the specification said so, because nobody had had cause to write it down. The stills are now converted to the delivered form like every other frame and the look is never applied to them, the rule lives where the deliverables are decided rather than where they are written, and the colour document says it out loud.

The same diagram was wrong a second time, in the other branch

The colour document's chain diagram had the viewing branch staying in the shooters' format after the grade is applied. That was true in the version written on the morning of 11 September, where the grade was a short numeric one and the conversion happened later. It stopped being true that afternoon, when the grade became a full colour file that already ends in the delivered form. The building work found it: the viewing transform has to start where the colour file lands, and the diagram said somewhere else.

The document was corrected rather than the code, and the property the sentence was there to protect survives the correction. The reason the viewing branch was described as staying in the shooters' format is that the video tool cannot carry values brighter than white through a resize without clipping them. That still holds, and for a better reason: everything unbounded now happens inside the single lookup table, where the colour engine handles it and the video tool never sees it.

A configuration point was removed rather than built

The tracker's columns were to be loaded from a template file the studio could edit, so its layout could change without a code change. That was the right shape while nobody knew what the columns were. They are known now, and a template loader would be a setting standing where a fact belongs: one more thing to configure, to ship a default for, to create on first run, and to get wrong. All of it is gone, and the settings page loses a section that had one entry in it.

The report the tool writes for itself went the other way. Five sheets, carrying what the tracker has no room for: every shot's timecodes, every delivered file's size and checksum, and a column for every single quality check, reading pass, fail or not-applicable. That last one needed the list of checks to exist in one place rather than being inferred from whichever ones happened to fail. Otherwise a check that passed everywhere silently has no column at all, and a video file reads "pass" on a check about image sequences that was never run against it.

The real shot tracker arrived, and a guess had stood in for it

The one thing the reporting work was waiting on was the studio's tracker layout. It has now been supplied as the live sheet itself: 790 shots across 55 turnovers. A placeholder layout had been written months ago to keep building against, eleven columns of what a tracker plausibly holds. Exactly one of those columns exists in the real sheet. Four more that it invented - duration, source timecode in and out, version, delivery path - have no column at all, and stay in the tool's own quality report where they were already recorded.

The more useful discovery is what the sheet is. Thirty of its thirty-nine columns are filled in by the vendor's team in the weeks after a delivery: who is working the shot, how hard it is, which review movie was sent back. The tool must never write those, so it produces rows to paste rather than a spreadsheet to hand over, and a re-export can not destroy a fortnight of someone else's tracking.

It also acted as a test of work already done. 628 of its 782 real filenames parse correctly under the naming rules built from the written spec, to the right kind of deliverable, and the ones that do not are older rows from before the convention existed. That is the first time any of this has met the production's own data.

Two settled answers did not survive contact with that sheet

Not everything is 24 frames a second any more. A check was made an error on the basis that the shooters conform all footage to 24, so anything else means a file escaped the conform. Every one of the 370 shots on the older turnovers is indeed 24. On the recent ones, 29 of 262 are not, mostly 23.976. Left as it is, that check would reject about one shot in nine of a current turnover, which is a rule that gets switched off rather than obeyed. What the sheet cannot say is whether that column records the edit's rate or the rate the camera shot at, and only the first would trip the check. That is now a question for the editor.

The check on the review movie's filename accepts none of the 55 real ones. It was written from the spec's pattern and kept on purpose after the tool stopped producing that file, so a human-typed name could still be checked. The real names carry a two-digit year and a token the spec never mentions, a third of them have no version, and the rest vary by capitalisation between five editors. A check that flags every correct file is worse than no check, so it is marked unusable until the tolerance is decided.

One diagram would have had the tool apply the same conversion twice

The colour document's chain diagram shows the delivered plate arriving in the wide scene-referred form after the grade is applied. Read as a list of steps, that says the tool performs the conversion itself. It must not: the grading session's colour file already ends there, so doing it again would convert twice.

Nothing would have failed. Every frame would have been written, every check would have passed, and every plate would have been wrong in a way that looks like a grade decision rather than a defect. The diagram now says it is a statement of where the pixels are rather than a step, the conversion lives in the code as its own named piece for the case that genuinely needs it, and the check that inspects each colour file for where it lands is what tells the tool which case it is in - rather than a filename.

The colour workflow was described properly, and it replaced the plan

The studio set out how colour actually works here: the shooters' colour is a starting point, the AD meeting decides the look, and a grading session builds it and exports one colour file per shot. The tool applies those files and authors nothing. Colour is therefore finished before the tool runs, where the plan had assumed the tool sat in the middle of it.

Three things left the plan on the strength of that. The four on-screen colour controls, specified that morning, are gone: colour is authored once, in the session, with the AD in the room. The turnover review movie is gone, because the session already produces one, which takes a day out of the estimate. And the delivered plates now carry the approved look rather than shipping untouched, which reverses a decision argued the same morning - defensibly, because that argument was that the grade moves later, and in this workflow it does not move at all.

None of it had been built. Two days of specification changed, and no code did. That is the cheapest possible moment for a change of this size, and it is the reason the colour work had not been started yet.

"Log encoded" was nearly read as "camera original"

The first description of the new workflow said the shooters deliver log encoded files per shot. That was read as camera original footage, and an entire apparatus was specified against it: a per shot record of which camera transform to apply, a translation table between two tools that name those transforms differently, and a new failure mode for an unrecognised name.

The studio then clarified that the shooters deliver one studio standard format, whatever they shot on. All of it was deleted the same hour. One format on every file means one conversion forever, and the camera-specific step stays where the camera information actually is. The correction cost an hour of writing because nothing had been built; it would have been a fortnight later.

The code now runs on the machine it is for

Until this week every test had only ever run on the Linux development machine. A hosted Apple Silicon runner now runs the whole suite on every change: 547 tests, lint and type checks, all green, and slightly faster than locally.

It also closed a gap nobody had measured. The development machine tests against the video tools its Linux distribution happens to ship, three major versions behind the ones the product will actually install. CI runs the real bundled tools, so the tested configuration and the shipped configuration are finally the same thing. The Apple hardware encoder was confirmed to start and encode, which was an open question that could only ever be answered on a Mac.

The target moved from Windows to macOS, and the design absorbed it

The primary user turned out to be on an Apple Silicon Mac. Windows and macOS swapped places: macOS is v01, Windows is the v02 backlog item macOS used to be.

It cost one line of application code. Core never imported Qt, used pathlib throughout, had no Windows API anywhere, and already ran its worker pool the way both targets require. All 547 tests passed on the new settings without modification. The rest was documentation and re-sourcing the bundled video tools.

That one line matters, though. The Windows tools were called ffmpeg.exe, so the Linux development machine looked for ffmpeg, missed them, and used its own copy by luck. The macOS tools are called exactly what Linux looks for, so the first fetch made every test fail at once. The lookup is now explicit about which platform the bundled tools are for.

The bundled video tools had to be replaced entirely

The Windows build came from gyan.dev, which publishes Windows builds only. That was checked rather than assumed: 419 downloads across the 100 most recent releases, not one of them for a Mac. The replacement is the martin-riedl.de Apple Silicon build of the same ffmpeg version, which carries everything the spec depends on and happens to be a quarter of the size, leaving real room under the installer budget.

Its features were confirmed by reading the downloaded binary, because an Apple Silicon program cannot be run on the development machine. That is good evidence, not proof. Whether the hardware encoder actually starts on the editor's Mac is a question only that Mac can answer.

A settled decision about colour turned out to be wrong

A fortnight ago the question of what the footage looks like when it arrives was asked, answered and closed. This week it was researched properly and the answer was the opposite of what had been recorded. The footage arrives log encoded: a flat, low contrast form that holds far more detail than a normal picture and is meant to have a transform applied before anyone looks at it.

The consequence was already shipped. The reference videos the tool produces apply no transform at all, which was correct under the old belief and produces a washed out picture under the true one. No test caught it and none could have: every test checks that the code does what it was told, and the instruction itself was wrong. It was found by asking the question again rather than by anything going bang.

The colour document was rewritten rather than patched, deliberately. Amending it would have left two readings side by side, and the wrong one was the one that read as settled. The handoff record now opens with a warning that anything written before this week about colour should be distrusted.

The camera question was removed instead of answered

Log encoding differs by manufacturer, and by camera generation within a manufacturer, and for some cameras by the sensitivity the operator dialled in on the day. Supporting that properly means knowing which camera shot every clip, and coping with a shoot that mixed two.

The shooters are converting their footage anyway before sending it, so they will be given a template project that converts to one camera-neutral format. The camera-specific step happens at their end, where the camera information actually exists. Three problems disappear rather than being solved, and the tool has one input format forever, whatever anyone buys next year.

The obvious choice of working format would have quietly destroyed colour

The natural instinct is to deliver plates in the same colour range as an ordinary television picture, since that is what everything is eventually viewed in. Cameras capture considerably more saturated colour than that range can hold, and squeezing the wider set into the narrower one pushes the excess into impossible values that behave badly in compositing software.

It is worse than a one-off loss: merely resizing such an image manufactures more of them, and this tool resizes every plate to make the HD version. The industry standard wide working space avoids the problem entirely and costs nothing extra, so that is what is being used. The film industry maintains a whole published specification for repairing this damage after the fact; not causing it is cheaper.

Writing the checks corrected the checklist twice

The rules document is the specification, so building from it is also the first real reading of it. Two rows did not survive. The delivery-folder writability check was filed as a per-shot check, which would mean one question asked a hundred times over a network drive for a single answer, and it also refused a destination folder that does not exist yet - which is the normal case, since the run creates it.

The 16 bit audio check was an outright failure in every case, but a sound file that arrives as a wav is delivered as an exact copy by design, so a 24 bit source delivers 24 bit and failing it would fail a deliverable that is precisely what the spec asks for. It is a warning there, and the warning is already raised earlier anyway. Both rows were corrected in the document with the reasoning attached, rather than the code being bent to match them.

The test turnovers had been quietly failing the real standards

Synthetic test media is 64 by 36 pixels and four frames long, because generating real 4k plates per test would take minutes. Once the rules existed, that media legitimately failed them: not 4k, far too short, no handles, no HDRI. The temptation is to soften the rules so the tests stay green. Instead the thresholds became settings the tests state out loud, which is what the settings page needed anyway, and the headless command gained a way to be pointed at a studio's own numbers.

Answering a question about sound found a bug in the picture

The reference mp4s mux the shot's audio, and it was an open question whether a turnover's sound covers the same span as its picture. The editor confirmed it does, cut point to cut point - which sounded like a confirmation and was actually a warning. If the sound ends with the picture, then an editor lengthening a shot into its handles runs past the end of the audio, and lengthening a shot that way is the documented way to do it.

ffmpeg was told to end the file when the shorter of the two streams ran out, so in that case it was cutting the picture short: 24 frames asked for, 12 delivered. The check added last week caught it rather than shipping it, but it would have failed a perfectly good render. The audio is now padded with silence instead, so the picture always wins and a wav that overruns is still trimmed. Both directions are pinned by tests.

A question carried for weeks rested on a premise nobody had checked

The lens distortion chart was the one row of the delivery table the tool did not produce, and three things about it looked undecided: the scan not recognising one, nothing to file it under, and no versioning rule for it. All three assumed it arrived as a clip on the timeline. It does not - it comes as a folder in the turnover package, and the scan only ever looks at clips, so it was never going to meet one. The question dissolved rather than being answered.

For this version the editor moves that folder across and renames it themselves. The tool is not silent about it, since the studio marks the lens grid Required: it warns when a turnover has none, and says so when there is one, because a manual step nobody is reminded of is one that gets forgotten.

The tool asks where the files are rather than hunting for them

The plan was to find the Google Drive mount by probing the two places Google documents it, since there is no G: drive on a Mac. The editor settled it instead: they point at a source folder and a delivery folder, and both happen to be on the Drive. That deleted a planned feature rather than adding one - nothing detects anything now, and first run has one less thing to get wrong on a machine nobody has seen. A wrong default would have been worse than none, opening the dialog somewhere plausible and empty.

It leaves one real question behind, now on the Mac list: a shooter working on Windows exports timelines carrying G:\... media paths, which mean nothing on the editor's machine wherever their Drive sits. The tool already falls back to searching the chosen source folder by filename, so this should resolve itself, but only a real turnover will say.

Three ways a reference encode goes wrong without failing

An image sequence states no frame rate, and ffmpeg invents 25. Every reference built from an EXR or DPX sequence would have played 4% fast, with nothing in the log to say so. The timeline rate is now passed explicitly, and as an exact fraction: 23.976 is 24000/1001, and a rounded rate drifts against the timecode.

Trimming a shot keeps the original timestamps, so the file opened with a gap as long as the trim. Measured: four frames of picture wrapped in a quarter second of container.

ffmpeg reports success when the source runs out early. Asked for 100 frames of a 4 frame plate it writes 4, exits cleanly, and the deliverable would have been recorded as finished. The frame count is now read back off the finished file and a short one is refused. That was a real defect, and it was a test expecting a failure that found it.

The reference encode trades progress for speed, deliberately

It hands the source to ffmpeg in one pass instead of pulling frames through the app, which would copy 95 MB per frame to hand straight back. The cost is that a reference goes from started to finished with nothing in between, and cancelling a run lets the encodes already running finish. Worst case is one encode per worker. Both are recoverable later if watching a real hundred shot run makes them matter.

ffmpeg does have an EXR encoder

CLAUDE.md said it did not. It does, but only none, rle, zip1 and zip16 compression, and it cannot write a timeCode attribute. The conclusion, use the OpenEXR bindings, was right; the reason was not.

Two QC rule IDs pointed at the wrong rules

COLOR_AND_FORMAT cited QC-022 for 8 bit sources (that is QC-020) and QC-040 for the audio bit depth check (that is QC-044).

QC-151 had no regex to check against

It requires every deliverable filename to re-parse, but only an input clip-name pattern existed. NAMING_SPEC section 7 now carries the output grammar, one anchored pattern per kind, verified against every example and against .part rejection.

The timeline frame rate is authoritative

Shooters set all footage to 24 in Resolve, so a rate baked into a file may be stale camera metadata. Frame math follows the timeline; what the media claims is kept separately so QC-026 can name the file that escaped the conform. Frame counts still use the file's own rate, because a file holds the frames it holds.

The two halves of the naming spec disagreed about versioning

Section 4 versions per shot; section 7 said a destination entry counts only if it matches the kind being planned. Section 4 wins, because it is the half that says why: partial version sets confuse downstream. Section 7 was corrected. A shot whose clean plate shipped at v01 therefore starts its main plate at v02.

DWAA is lossy, so "pixels in, pixels out" has a limit

At level 45 a written frame comes back about a tenth of a percent off, proportionally. It means no colour transform is applied, not that the file is a byte copy. QC hashes the written file instead of comparing pixels, which holds because the encoder is byte-deterministic.

A failed job is a result, not an exception

A hundred shot run cannot stop because one row is broken, so every job comes back with a record whatever happened: written, failed with a reason, or skipped because the run was cancelled. The new QC-100 carries the reason, and every other post-render check reads NA behind it, because there is no file to check.

The worker pool spawns on Linux too, deliberately

macOS defaults to spawn and Windows can do nothing else, so the target has never been able to fork. Spawning on the Linux dev machine as well means the constraints on what can cross into a worker are identical in testing and in the field, instead of a job that only works under fork passing every test here and failing on the user's machine. This survived the move from Windows to macOS untouched, which was rather the point.

Atomic writes and ffmpeg's format guessing collide

Every deliverable is written to a .part name and renamed, so ffmpeg never sees the real extension and refuses the output: it picks a muxer from the extension, and .wav.part tells it nothing. Every ffmpeg-written deliverable has to name its format outright. Found by a test.

The witness cam gap in the spec table means nothing, and now says so

Every other raw sequence row in the shooters' table shows a frame range and two subfolder-naming columns; the two witness cam raw rows show a bare filename with neither, which reads as a single file rather than a sequence. It was carried as an open question because it looks deliberate. It is not: the editor confirmed that wit is a normal deliverable, treated exactly like any other clip on the timeline, so it owes the same four picture outputs and no audio. The build already did that, so nothing changed except that the next person to read the sheet will not go looking for a rule that was never there. OQ-5 is closed.

The sheet arrived as a spreadsheet export as well as a PDF this week, and reading the whole table in text turned up five defects of that same kind, including an HDRI row whose filename ends .mp4 and two rows given the same label where one is plainly the 4k version. All five are now listed side by side with what the tool actually does. None of them changed the build: every one was already implemented the right way.

ffmpeg's scaler quietly clamps float to 0-1

It was recorded as "swscale cannot carry float", which understated it. It accepts float in and out and flattens everything above 1.0 to white: 4.0 in, 1.0 out. Harmless today because every accepted source is integer and bounded, and a live hazard the day the EXRs move to scene linear. It is why the EXR path resamples in numpy.

Two ways a decode goes wrong without failing

The raw pixel format is planar G, B, R, so reading it in order swaps red and blue on every deliverable. And unless ffmpeg is told to pass frames through untouched, it may duplicate or drop them to hit a constant rate, breaking the one-to-one mapping from source frame to delivered frame. Both are pinned by tests that compare a range against a full decode of the same media.

Three things ffprobe does that the tests pinned down

It invents 25/1 for a single EXR frame; it exits 0 on a corrupt EXR while reporting a 0×0 stream, so QC-014 cannot trust the exit code; and it cannot state a frame count for an image sequence.
