| OQ-7 | ~~Downscale for EXR-source path~~ **RESOLVED 2026-09-10**: neither. `core/resize.py` implements antialiased Lanczos-3 in numpy, the same filter `scale=1920:1080:flags=lanczos` applies on the container path, so the two paths agree: on a hard edge the outputs are identical, and on smooth content they differ by under one 8 bit level. `scipy.ndimage.zoom` was rejected because a cubic spline does not antialias (a 2:1 reduction samples the source instead of integrating it) and it would add a large dependency to a 300 MB installer budget | numpy Lanczos-3, no new dependency | no |
| OQ-8 | ~~ffmpeg licensing and source~~ **RE-RESOLVED 2026-09-10 for the macOS target**: gyan.dev publishes Windows builds only (419 assets across 100 releases checked, zero macOS), so the Windows pin is gone. v01 bundles the **martin-riedl.de macOS arm64 GPL v3 build, ffmpeg 9.0.1**, which carries libx264, libzimg for `zscale`, libfreetype for `drawtext` and `h264_videotoolbox`. The licensing reasoning is unchanged and still holds: GPL v3 applies to the binaries alone, ProIngest calls them as subprocesses and is not linked against them, and the tool stays inside the studio so no source offer is triggered. Settings override retained. Rationale, rejected alternatives and the verification method are in `proingest/resources/ffmpeg/PROVENANCE.md` | martin-riedl.de macOS arm64 GPL build, x264 with CRF as specified | no |
| OQ-9 | **Apple Developer ID for signing and notarization?** Confirmed 2026-09-10 that there is no account today. The bundled ffmpeg binaries are already Developer ID signed with the hardened runtime, so they are not the problem; ProIngest's own bundle is. Workarounds in PACKAGING.md: buy a Developer ID ($99/yr), or transfer the app by a route that never sets `com.apple.quarantine` (scp, rsync, USB), or run `xattr -dr com.apple.quarantine` once on the target machine | Unsigned, handed over without quarantine, xattr stripped on install | **yes, before handover** |

| OQ-17 | ~~Color space conflict~~ **RESOLVED 2026-09-10 by the studio**: the turnovers arriving today have the sRGB curve **baked in on every file, the EXRs included**, so the source is display referred. Reference encodes apply **no** transfer from a baked source and the linear-to-sRGB curve only from a scene linear one; raw EXR output is untransformed either way and states which it is in `proingest/colorspace` | `srgb_display`, switchable in Settings | no, M3 unblocked |

| OQ-20 | **Lens grid deliverable is not planned yet.** The type table lists a png copy per lens grid, but three things are undecided: the scan does not recognise a lens grid clip at all (it currently fails the shot naming regex and lands as QC-010), a lens grid is turnover-level so it carries no show to place it under `<delivery_root>/<show>/_turnovers/`, and section 4 defines versioning per shot and says nothing about a per camera/lens/mm deliverable. Answer with a real turnover alongside OQ-4 | Not built. Nothing else depends on it; QC-054 already warns when a turnover has no lens grid | no |
| OQ-21 | **Alpha from a container source.** Section 3 says raw EXR output keeps alpha when the source has a real one. The EXR source path does: `exr.read_pixels` returns whatever channels the file carries. The container path decodes `gbrpf32le`, which is RGB only, so a ProRes 4444 alpha is dropped. Two things are undecided: what counts as a *real* alpha rather than an opaque one the codec always carries, and whether a plate consolidated out of Resolve ever legitimately has one. `MediaInfo` records no alpha field today, so nothing could set the flag even if the decoder took one. Answer with a real turnover alongside OQ-3 | RGB only from a container; alpha preserved on the EXR path. Decoding `gbrapf32le` is a one line change once there is something to switch on | no |
| OQ-22 | **No Mac is available to build or test on** (confirmed 2026-09-10), and PyInstaller cannot cross-build a `.app`. So M7 cannot be completed here, and nothing has ever executed the test suite on macOS or on arm64. Which route: a GitHub Actions `macos-14` runner, or building on the editor's own machine at handover? | Assume a CI runner will be added at M7; keep everything else verifiable headless on Linux | M7 only |
| OQ-23 | **VideoToolbox quality is uncalibrated.** `h264_videotoolbox` has no CRF; on Apple Silicon it takes `-q:v` on a 1-100 scale with no published mapping to x264 CRF 18. Separately, a codec compiled into the binary is not proof it opens a session on the actual hardware, and that can only be learned by running it. Both need the target Mac | Default to software x264 CRF 18, which is what the spec pins; hardware encode opt-in and labelled an approximation; detect by trial encode, not by string match | no |
| OQ-24 | **Is every machine that will run this Apple Silicon?** The bundled binaries are arm64 Mach-O and will not run on an Intel Mac, since Rosetta translates x86_64 onto Apple Silicon and not the reverse. Answered as Apple Silicon on 2026-09-10 for the primary user, but a second machine in the studio would break silently at the first ffprobe call | arm64 only; if an Intel Mac appears, add a universal2 bundle or a second lock entry, at a cost in installer size | no |
| OQ-25 | **Where does Google Drive actually mount on the editor's Mac?** Current Google Drive for desktop uses `~/Library/CloudStorage/GoogleDrive-<account>/My Drive`, older versions `/Volumes/GoogleDrive`. The `<account>` segment differs per machine, and this drives first-run detection, the file dialog default, and whether the FR-2 path map is needed at all. If the shooters are also on macOS the map may be empty in practice | Probe `~/Library/CloudStorage/GoogleDrive-*/My Drive` first, then `/Volumes/GoogleDrive`; fall back to the last used folder | no |
