# QC Rules

Every rule has a stable ID, a phase, a severity, and a scope. **Since 2026-10-07 (user) nothing prevents rendering a batch or a turnover.** "Individual shots can get blocked from rendering if there is missing media, or the amf, clf or an appropriate cdl are missing so the tool cant recreate the colors. In that case, the individual clip stays unrendered until the issue is fixed and rescanned." So:

- **`error` on a row holds that shot back** and nothing else (`planner.holding_errors`); every other shot renders. The errors left are the ones with nothing to render or no way to colour it: no file, two files, an unreadable or undecodable file (QC-012, 013, 014, 022), no name to give it (QC-010, 011, 065), no cut or two (QC-066, 067), an edited In/Out that cannot be (QC-031, 032), or a grade the tool cannot rebuild (QC-046, 047, 075 when two AMFs claim it, 076). A turnover whose folder has moved holds its rows (QC-069), since their media is missing.
- **An `error` at batch scope stops the run** with a popup: a delivery root that is not writable or has too little space (QC-062, 063). Nothing else does (`qc.must_fix`).
- **`warning` and `info` never block.** A warning colours the row amber; both are logged, and every one is written, in words, to the QC log's **Issues** sheet (user: "expand the qc list that gets exported afterward to pick up non-blocker issues"). The Fix-it report leaves info out.
- The media is still probed, to decode it; **it is not used to second-guess the timeline** (user: "Use the edl's source and record timecodes for each event and don't qc by probing the media"). See QC-029.

Before 2026-10-07: two tiers from 2026-09-23 (D8, D9), any must-fix anywhere stopping the whole run, with Accept As Is (QC-074) to run a turnover past its errors. Phase B (QC-1xx) is unchanged: a failure there fails the row and names the output. All results appear in the QC log.

Rule IDs never change meaning. New rules get new numbers. **The one exception is a rule revised on
the same day it was written, before any code, log line or spreadsheet has used it**, which is what
happened to QC-009, QC-019 and QC-039 on 2026-09-11. The grade carrier was specified as a CLF, then
as a CDL, then as a CLF again, all in one session and none of it built, so these three were written,
reworded and written back. On 2026-09-18 the carrier became the CDL for good, applied in ACEScct,
with the built rules amended in place and dated rather than renumbered, because the failure each
one names did not change. Nothing anywhere had ever referred to them, which is the only condition
under which this is safe. **It is not a precedent**: the moment a rule ID reaches code, a log or a
spreadsheet, it is frozen and a changed rule gets a new number.

A rule whose reason for existing goes
away is marked **RETIRED** and its ID is left in the table rather than deleted, so a log line or
a spreadsheet column from an older run still resolves to what it meant when it was written.

**"Fix in Resolve - " (user, 2026-10-05).** An error whose fix is in Ben's Resolve session (his
timeline, metadata, or the EDL, CSV, AMF and CLF exports) leads its message with these words:
QC-001, 002, 004, 010, 011, 046, 047, 065, 066, 067, 071, 073, 075, 076, 079 and 082
(`models.RESOLVE_FIX_RULES`; QC-008 and QC-029 left it on 2026-10-07, one retired and one now
info). Errors and warnings; an info line from the same rule does not.

## Phase B: post-render verification (QC-1xx)

Run per deliverable **on its temp, before the rename** (D11, F11 of `docs/REVIEW_2026-09-23.md`). A deliverable that passes takes its final name; one with any error is deleted, is recorded as failed with the rule that failed it, and leaves the row not done. **There is no `.failed` sidecar** (user, 2026-09-23). The row waits: the next Run leaves it alone until the editor fixes the cause and right-clicks **Re-scan** on the shot or its turnover (2026-09-25; was Reset), and then the whole shot runs again, at the next version if anything of it landed.

QC-100 is the exception to that: it reports a render that never produced a file at all, so there is nothing to keep and nothing to mark. A render failure leaves no `.part` and no destination, by design.

## QC log structure

`qc_ingest_log_<batch>_<date>.xlsx`

- Summary: batch name, date, tool version, turnovers, rows, rows delivered / skipped / **held back** / failed, rule counts by severity. The "QC bypassed (QC-074)" line went with Accept As Is (2026-10-07)
- Shots: one row per shot row. Columns: turnover, source file name, shot code (from `Shot`), clip type (from `Shot Type`), source path, source fps, source res, snapshot In/Out (frames and TC), final In/Out, duration, max available, audio path, edited, **source encoding** (`Gamma Notes` + `Color Space Notes` verbatim, rather than the colour space they resolve to, empty when the row named none), **Source codec, pixel format, bit depth, chroma, primaries, transfer, matrix, range** (the media file as ffprobe reads it, so whoever checks a turnover sees whether it is usable for VFX: an 8 bit 4:2:0 clip labelled BT.709 shows at a glance. A colour tag the file does not state reads `not stated`; a row with no media leaves all eight empty. Reported, never blocking; QC-020 is the rule that warns. Added 2026-09-24 at the user's request), **Grade** (the CDL from the row's EDL event as `*ASC_SOP` / `*ASC_SAT`, empty when the row rendered ungraded), skip reason, warnings (IDs), errors (IDs)
- **Issues** (2026-10-07, user: "expand the qc list that gets exported afterward to pick up non-blocker issues"): **every finding in words**, one line each: turnover, shot code, clip name, rule, level, **Effect** (`stopped the run` for a batch error, `held this shot back` for a row's error, `rendered` for everything else, or the deliverable and its status for a QC-1xx), and the message, so "Clip ungraded in Resolve project" and "Plate was 260 frames on the timeline" read as written. Records of what the tool did (QC-048, 060, 061, 080, 085) are left off (`exports.RECORD_ONLY_RULES`)
- Deliverables: one row per deliverable. Columns: shot code, elem, kind, res, version, path, frames, size bytes, checksum (or first/last frame hash for sequences), then one column per QC-1xx rule with PASS/FAIL/NA

Four sheets since 2026-10-07 (Issues added); three from 2026-09-22, when the Side Files and Camera Data sheets went with the HDRI and camData deliverables they described.

`shot_tracker_<batch>_<date>.xlsx` is written to be **pasted into the studio's own tracker**, so its
columns are that tracker's columns and not a layout of ours. **OQ-2 is answered** from the real
sheet (`docs/Pre Pro Shot Tracker - W1.csv`, 790 rows across 55 turnovers). The guessed default
that used to be described here shared exactly one column with it, Shot Code, and is gone.

production state that the vendor's team fills in over the weeks after delivery - statuses,

The export is **additive**: **one line per shot code** (user, 2026-09-23), as the studio's sheet
