# Review of 2026-09-19: assumptions in the plan, and what the session settled

Written for the user. `PROGRESS.md` section 1 is the handoff record for the next session and
`docs/OPEN_QUESTIONS.md` is where every open item below lives with an ID; this page is the
readable account of one review, kept because the misalignment it found is worth reading whole.

## Why the review happened

You suspected the plan and the actual workflow had drifted apart, and asked for a pass over the
repo looking for assumptions about the system working as planned: research what can be
researched, ask what cannot. One agent audited the code for assumptions the docs do not record;
the Resolve and ffmpeg facts were researched online; the rest were put to you.

## What the review found

**The spec was built on a wrong premise for a week.** Every colour and format document said the
shooters deliver ProRes 4444, 12 bit, full range, and QC-020 and QC-021 were built to it. They
deliver camera-native files, trimmed in Resolve by Copy with trim. That single fact moved most
of the rest:

- QC-021 warns on every real source and QC-020 blocks 4:2:0 modes that real cameras record.
- The decode passes no range or matrix flag and never checks one, while the docs describe a
  "forced" decode and a QC-018 check that were never built. With native files this is less
  dangerous than it looked, because Sony and Canon record their log full range and flag it, but
  it is still an assertion the tool has to make rather than a default it happens to get.
- ffmpeg decodes every common compressed camera codec and no RAW format. A Blackmagic camera
  recording BRAW cannot be read at all; the same for REDCODE, ARRIRAW, Cinema RAW Light, X-OCN,
  N-RAW, ZRAW and ProRes RAW.

**OTIO was never part of the real workflow.** The tool's shot list is built entirely from an
OTIO exported by the shooters, and the shooters export nothing for the tool. Ben's EDL with the
CDL is the only timeline the tool will ever see. That is a redesign of the scan, not a setting.

**Clip names carry extensions** and the naming regex, media matching and EDL matching all
assume they do not. Cheap to fix, and unrecorded until now.

**Unrecorded code assumptions that survive the reversal:** the approved cut is dropped silently
when the media has no timecode while the CDL is still applied; a file at another rate has its
timecode counted at the timeline rate; media matching is case sensitive where EDL matching is
not; the docs promise letterboxing and the code squashes; Drive streaming placeholders are
indistinguishable from files. Retimes and compound clips would render wrong frames silently, but
you confirmed they never occur, so the right shape is a check that refuses them.

**Confirmed rather than assumed:** Resolve's CDL export is node one only, Lift, Gamma, Gain,
Offset and Saturation, Luma Mix at 0, one video track, no transitions, no compound clips.
Generate LUT bakes the node graph and not project colour management. Resolve trims long-GOP
codecs without recompressing since version 15. The worker pool and the frame math are sound.

## What you decided this session

1. Sources are camera-native, whatever the cameras shoot. No ProRes 4444, no EXR.
2. Clip names carry extensions.
3. Shooters hand consolidated timelines to Ben and export nothing for the tool.
4. Ben works in ACEScct, grades in node one, and exports the CDL by right-clicking the timeline.
   That EDL is the tool's sole source of trims and colour. No OTIO.
5. No speed changes, reversals or freezes.
6. 4:2:0 sources are allowed with a warning. QC-020 becomes a warning.
7. If a shooter leaves the camera input transform out, a per-turnover pulldown supplies the
   default. Two details are still yours to decide (OQ-59).
8. Google Drive: mirror mode on the editor's Mac, with the source root and `_color` available
   offline. Ben's setting only affects whether his exports appear promptly.

## Later the same day: the sample turnover arrived

The user dropped `Turnover199/` into the working tree: five Sony A7V clips as Resolve's Copy
with trim wrote them, a `.drt` timeline and a Media Pool metadata CSV. `docs/SAMPLE_TURNOVER_199.md`
is the evidence page. What it settled, against the plan above:

- **The camera file does not carry the input transform after the trim.** Resolve rewraps the MP4
  and strips Sony's `rtmd` metadata track; the transfer, primaries and matrix read `unknown`. Route
  (a) of OQ-58 cannot be built. The encoding is named in exactly one place in the sample, the
  CSV's `Gamma Notes` (`S-Log3`) and `Color Space Notes` (`S-Gamut3.Cine`). Who filled those
  fields, Resolve or a script, is OQ-68 and is the user's to answer.
- **The decode is a matrix off, measured.** With no matrix declared, ffmpeg decodes these UHD files
  with BT.601 coefficients; an explicit BT.709 decode differs on 97% of pixels. OQ-60 is now a
  blocker before any Sony plate ships.
- **The shooters produce a timeline file after all, without exporting one.** Media Management
  writes a `.drt` beside the trimmed media (manual, 18.6), and it carries the timeline rate, record
  positions, source starts and the 24-frame handles that an EDL cannot, and no grade. Whether it
  reaches the tool is OQ-68; what the scan reads is OQ-57.
- **Clip names were not renamed.** The clip name is the camera filename with its extension, the
  shot code sits in the `Shot` metadata field, and nothing carries the element type (OQ-62).
- **The file is 23.976 and Resolve is 24.000**, with `IsForceConformed` set on every clip (OQ-69,
  and it decides OQ-19's question for this camera).
- **Copy with trim** keeps timecode, adds one second of handle either side, writes an audio track
  into every file, and drops all camera metadata (OQ-61, answered).

Still wanted from the user: the answers to OQ-68, one original camera file or its `M01.XML`
sidecar, OQ-59's two decisions, and whether clips are renamed or the code travels in metadata.
